# AI-agent для OpenWrt

Локальный AI-агент для OpenWrt 25.12 (сейчас — Тула, VM 100 на Proxmox; ранее физический NanoPi R76S, теперь холодный резерв). Ядро диагностирует сеть, AdGuardHome, netshift/sing-box, zapret и общесистемное состояние через ограниченный набор структурированных tools. `sys_inspect` даёт read-only доступ к firewall/nftables, маршрутам, интерфейсам, портам, установленным NAT-соединениям (conntrack), процессам, сервисам, пакетам, файловым системам, UBus и безопасному представлению UCI. `sys_resource_usage` показывает загрузку CPU по ядрам, температуру, память и место на overlay. Изменения всегда проходят через детерминированный plan/diff, локальное подтверждение, бэкап, проверку исходного хэша и action-specific verifier.

Дополнительно:

- **`firewall_open_wan_port`/`firewall_close_wan_port`** — открыть/закрыть TCP/UDP-порт роутера со стороны WAN (сервис на самом роутере, не port-forward на LAN). Denylist управляющих портов (SSH/DNS/HTTP(S)/админки) не открывается даже с подтверждением. План и верификация отдельно сообщают `listener_present`: правило без слушающего сервиса даёт снаружи «connection refused», и агент обязан сказать об этом, а не отчитаться об успехе.
- **`ssh_open_wan_access`/`ssh_close_wan_access`** — внешний SSH одним действием: отдельный экземпляр dropbear на нестандартном порту (>1024, вход только по ключу, пароли выключены) плюс firewall-правило `src=wan ACCEPT`. Verifier требует, чтобы сокет принадлежал именно `dropbear`, параметры запрета паролей сохранились, а UCI- и nftables-правила точно совпадали с планом. Требует непустой `authorized_keys` на роутере; штатный dropbear на порту 22 остаётся LAN-only и не трогается.
- **Многошаговые запросы** — запрос вида «закрой порт X и открой ssh на Y» состоит из нескольких mutating-действий, а активное действие в ядре всегда одно. После каждого подтверждённого и проверенного действия `AgentCore.confirm` даёт модели ещё один ход и возвращает его результат в поле `follow_up`: Telegram-клиент и CLI показывают следующий шаг с собственной кнопкой подтверждения. Цепочка обрывается при отказе пользователя, непройденной верификации или по достижении `FOLLOW_UP_CHAIN_LIMIT` (8 шагов на один запрос) — автономно изменения не применяются, каждый шаг требует подтверждения.
- **`sys_package_install`/`sys_package_remove`** — установка/удаление пакета через `apk` с планом, бэкапом world-файла и верификацией.
- **Роутинг между моделями** (`ai_agent/model_router.py`) — простые read-only вопросы уходят на дешёвую/быструю модель, сложные диагностические и все mutating-запросы — на более сильную; настраивается через UCI (`simple_model_id`/`complex_model_id`/`model_routing_enabled`).
- **Проактивный мониторинг логов** (`ai-agent-log-monitor`, cron) — раз в `log_monitor_interval_hours` часов (по умолчанию 4, настраивается в LuCI на вкладке Runtime) группирует повторяющиеся строки до передачи LLM и присылает короткий алерт до 900 символов только при реальной проблеме. Плановое окно `netshift subscription_update`, штатные `cron.err`-запуски и собственные INFO-строки агента (busybox пишет stderr демонов под `daemon.err`, из-за чего они выглядели подозрительными) отфильтровываются детерминированно. Повреждённый DNS-ввод AdGuardHome (`unpacking … err="bad rdata" / "buffer size too small" / unexpected EOF`) не порождает алерт вообще, сколько бы его ни было: fw4 заворачивает весь LAN-трафик на udp/53 в AdGuardHome, поэтому любой не-DNS на этом порту (например, QUIC-туннель на телефоне) неизбежно попадает в парсер; AdGuardHome такие пакеты отбрасывает и продолжает работать. Счётчики по типам остаются в метаданных запуска для диагностики.
- **Telegram-клиент** (`ai-agent-telegram`) — тонкий клиент к Core API с confirm/rollback-кнопками, markdown→Telegram HTML форматированием, индикатором "печатает" и безопасным разбиением длинных сообщений.
- **`agh_diagnose_domain`/`netshift_service_health`** — многослойная диагностическая "воронка" для домена/сервиса (сервис жив → firewall/DNS-перехват → DNS-тест через AGH и напрямую → активный трафик), а не единичная ad-hoc проверка. `agent_audit_log` показывает журнал именно действий агента (plan/confirm/apply/verify/rollback), не ручные правки по SSH.
- **Baseline нормального состояния** (`sys_baseline_compare`, `ai-agent-metrics-sample`, cron раз в 10 минут) — фоновый сэмплер копит в `metrics.sqlite` историю CPU, свободной памяти, conntrack, WAN-задержки, packet loss и числа LAN-клиентов; tool сравнивает текущее значение с эмпирическим p5/p50/p95 за последние N дней, чтобы отвечать не «conntrack=58000», а «это в разы выше обычного диапазона». При малой истории честно возвращает `insufficient_data` вместо выдуманного вердикта.

## Установка

На OpenWrt 25.12 с `apk`:

```sh
scp -r ai-agent root@10.110.112.1:/tmp/
ssh root@10.110.112.1 /tmp/ai-agent/install.sh --no-start
```

Создайте секрет непосредственно на роутере, не добавляя его в git или UCI:

```sh
umask 077
printf '%s\n' 'YANDEX_AI_STUDIO_API_KEY=...' > /etc/ai-agent/secrets.env
/etc/init.d/ai-agent restart
```

Проверка и интерактивный CLI:

```sh
ai-agent-cli health
ai-agent-cli chat
ai-agent-cli chat 'какая нода активна в ai_section?'
```

`install.sh` идемпотентен: обновляет код и init-скрипт, но сохраняет существующие `/etc/config/ai-agent`, `/etc/ai-agent/system_prompt.md`, секрет и `/var/lib/ai-agent`. API-ключ можно передать только файлом через `--secret-file`; аргумент с самим ключом намеренно не поддерживается.

## LuCI

После установки страница агента доступна в **Сервисы → AI Agent** или напрямую:

```text
http://<адрес-роутера>/cgi-bin/luci/admin/services/ai-agent
```

На странице видны состояние Core и Telegram, выбранные модели, LLM routing и
текущее действие. Там же можно менять основные несекретные UCI-настройки
(включая интервал фонового анализа логов, вкладка Runtime) и перезапускать
только Core либо Telegram. API-ключи, токен Telegram и пути к секретам
намеренно не показываются и не редактируются через LuCI.

Сохранение настроек в LuCI коммитит UCI и запускает reload ai-agent: помимо
обычного перезапуска Core, `reload_service()` в `/etc/init.d/ai-agent`
перегенерирует cron-строку `ai-agent-log-monitor` из `log_monitor_interval_hours`
и перезапускает cron — новый интервал начинает действовать сразу, без ручной
правки crontab.

## Core API

MVP слушает JSON Lines на Unix-сокете `/var/run/ai-agent.sock` с правами `0600 root:root`. Запрос:

```json
{"method":"chat","params":{"session_id":"optional","message":"проверь chat.z.ai"}}
```

Методы: `chat`, `confirm`, `rollback`, `reverify`, `history`, `health`.
`debug_uci` доступен CLI/root-клиенту, но не зарегистрирован как LLM tool. Переход
к HTTP в MVP намеренно отсутствует.

## Telegram worker

Long polling хранит подтверждённый `offset` в
`/var/lib/ai-agent/telegram-offset.json` с правами `0600`. Offset сдвигается только
после полной обработки update и успешной отправки ответа. Подготовленный Core/LLM-ответ
временно сохраняется там же до доставки: после сетевой ошибки или рестарта worker не
повторяет LLM-вызов либо mutating-action. Для каждого сообщения и его chunks хранится
отдельный checkpoint, поэтому повтор продолжает каждое сообщение с первой недоставленной
части и не дублирует уже полностью отправленные сообщения. Runtime-состояние доступно в
`ai-agent-cli --json health` → `telegram`; `ready` означает успешный свежий
long-poll, `degraded` содержит безопасную причину и текущий backoff, `stale` —
отсутствие успешного polling более 90 секунд.

## Безопасность

- Нет generic shell tool и нет `shell=True`; команды имеют фиксированный executable/argv allowlist, timeout и лимит вывода.
- Управление установленными procd-сервисами доступно через `sys_service_control`, но каждое действие требует отдельного подтверждения; управление самим `ai-agent` запрещено.
- Специализированные config-tools строят allowlist-представления. URL подписок, UUID/Reality-ключи, пароли и API-токены не отправляются модели.
- Результаты tools маркируются как недоверенные данные. Решение `read_only`/`mutating` и verifier задаются статически кодом.
- Одновременно может существовать только одно mutating-действие. Перед apply проверяются TTL, `uci changes` и SHA-256 целевых файлов.
- Для UCI сохраняются и `uci export`, и побайтовая копия `/etc/config/<package>`. Откат требует отдельного подтверждения.
- Незавершённые `confirmed`/`applying` после падения переводятся в
  `manual_review`; стабильный `rollback_pending` сохраняется для явных
  `reverify`, отката или решения оставить изменение.
- Секрет хранится только в `/etc/ai-agent/secrets.env` с правами `0600`.


Для проверки Telegram и других сервисов через netshift используется `netshift_service_health`. Он различает настроенный маршрут, наблюдаемый активный трафик и фактическую доступность на клиенте. Ping fake-IP, одиночный запрос с самого роутера и `zapret/dwc.sh` сами по себе не считаются доказательством отказа.
`agh_add_user_rule_exception` намеренно не реализован в MVP: безопасный авторизованный REST-путь AdGuardHome пока не настроен, а конкурентная перезапись YAML слишком рискованна.

## Тесты

```sh
python3 -m unittest discover -s tests -v
```

Интеграционные mutating-тесты выполняйте только с тестовым доменом `test-ai-agent-canary.invalid` и готовой параллельной SSH-сессией. CLI никогда не применяет plan без ответа `y`.
